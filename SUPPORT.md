# Support

## Usage and integration questions

Before opening a request, check:

- the [README](README.md) and [examples](examples/README.md);
- the [stable API/ABI contract](docs/api/APTA-API-ABI-1.0.md);
- the [specification](specification/APTA-SPEC.md);
- existing GitHub issues.

Use the **Support or integration question** issue form for reproducible build,
packaging, API-usage or platform-integration questions. Include the package
version, platform, compiler or ESP-IDF version, build options and the smallest
reproducer available.

## Bugs

Use the **Library bug report** form. Container/parser reports should state
whether the input may be shared publicly and attach a minimized non-sensitive
fixture when possible.

## Specification proposals

Normative changes, new conformance requirements and container extensions belong
in the **APTA specification proposal** form. A proposal must identify its
compatibility effect and whether it targets errata, a backward-compatible minor
version or a future breaking version.

## Security vulnerabilities

Do not open a public issue. Follow [SECURITY.md](SECURITY.md) and use GitHub
private vulnerability reporting.

## Support boundary

The project does not guarantee individual response times. Maintainers prioritize
security reports, regressions in supported versions, reproducible portability
failures and specification interoperability issues.
